# 选股任务唯一执行与验收合同

依据：用户在 2026-09-12 的明确纠正。本文记录用户要求，不从现有代码推导需求。

> 区别就是一个是自动任务 一个是开关型再跑一遍

> 这样我们才能在后续开发的时候迭代，只要手动触发成功 就是线上成功

> 你优先保证不要再犯一样的错误再解决眼下的问题

## 必须满足

1. 定时器和按钮仅负责触发，共用同一个完整任务：取数、选股与开仓判断、
   保存输入与结果、生成消息、经同一生产投递器发送。
2. 同样的目标交易日、配置、原始事实和初始状态，从两种入口运行，业务结果、
   持久化内容和消息正文必须一致。仅运行编号、真实执行时间及投递追踪信息可不同。
3. 当天已经运行过，再按按钮也必须重新计算、保存本次结果并再次推送。
   同一个请求编号的网络重试不重复执行或发送；新的按钮操作使用新的编号。
4. 不得以“手动只读”“仅核查”“重放早盘消息”替代完整任务。
   不得以手动标志切换计算、落库或消息模板。
5. 日期决定数据接口，已提交的每日状态不得重复推进。这些是两种入口共同执行的
   数据一致性规则，不能成为另设手工捷径的理由。
6. 消息使用普通交易语言，明确股票、对应推荐日期、建议操作和实际生效时间。
   不把内部对象名称、D0/rank 或模型编号当作操作说明。

## 阻止再次发生的检查

- 回归检查必须先在原错误代码上失败，并保存失败原因；不得将预期改为接受原错误。
- 空白交易日：两个入口分别从相同初始数据库运行，验证完整流程一致。
- 已有当日结果：新编号触发后，确认重新调用计算、产生新结果及新推送，且使用普通
  选股结果的存储与渲染合同；同编号重试不得重复推进每日状态或重复发送。
- 验证放行、不放行、缺少数据、计算失败、落库失败、投递失败；失败不能被包装成成功。
- 真实 PostgreSQL 与投递器测试必须通过。CI 的镜像发布依赖这些检查。
- 部署后核对提交，再用按钮实际运行生产任务；成功证据必须同时包含计算、落库和
  投递确认。HTTP 已受理、服务健康、只读核查或单独的消息送达都不能代替。

## 需求与历史材料的优先级

用户后续明确指令优先于本文。本文优先于此前相冲突的设计说明、旧测试和验收报告。
历史报告保留事实，但不得将旧“核查成功”解释为本合同通过。
如后续修改改变上述合同，必须明确指出具体改变；不能暗中增加例外再写进文档。

## 实现与验收位置

- 定时入口 `_commit_entry_from_bundle` 和按钮入口 `trigger_morning_selection` 都调用
  `V20Service._execute_selection_task`。HTTP 路由不再判断早盘、盘后或当日是否已有结果。
- `selection_runs` 保存每次新运行的输入、完整结果及对应推送事件。首次运行在同一
  数据库事务内推进每日状态；之后的运行保存新的普通 `ENTRY_DECISION`，每日状态只推进一次。
- 同编号重试读取已保存的本次运行。新编号重新计算、保存和发送；不是重发旧消息。
- `accepted=true` 表示受理，`calculation_result=SUCCESS` 表示计算完成。
  只有对应结果在生产投递器中达到 `SENT`，`task_success` 才为 `true`。
  `PENDING` 或 `DELIVERY_UNKNOWN` 都不能作为上线验收成功。
- `tests/unit/web/test_selection_task_contract.py` 保存原错误的行为回归检查。
  `tests/integration/data/database/test_v20_outbox_postgres.py` 验证 V22 放行与阻断、
  两种首次触发、并发同编号重试、事务回滚、普通推送及回执丢失。
  真实市场取数与计算入口的对照另由现有 canonical / morning selection 测试覆盖。

验收记录见 [2026-09-12 生产验收](acceptance-20260912.md)。后续修改仍必须重新通过上述
检查，并按实际部署提交保存生产任务结果与投递确认，不能沿用旧版本的成功记录。
